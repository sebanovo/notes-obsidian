17. Describir 5 características de software que tengan similitud con un producto real.
- **Diseño y arquitectura funcional**
    Un auto o una mesa requieren un diseño industrial detallado antes de construirse. El software requiere una arquitectura de sistema, diagramas de flujo y diseño de interfaz para definir cómo interactuará el usuario y cómo funcionará internamente.
    
- **Control de calidad y pruebas**
    Un producto físico pasa por control de calidad para verificar que no tenga defectos mecánicos o imperfecciones. El software pasa por una etapa de pruebas (QA/Testing) para identificar y corregir errores (_bugs_) antes de llegar al usuario final.
    
- **Garantía y mantenimiento**
    Al comprar un electrodoméstico, se cuenta con soporte o reparaciones ante fallas. El software incluye periodos de soporte, parches de seguridad y mantenimiento correctivo para subsanar errores que aparezcan durante su uso.
    
- **Iteración por versiones (Generaciones)**
    Los productos físicos lanzan nuevas versiones o modelos cada año con mejoras (ej. un teléfono o un automóvil). El software se actualiza mediante versiones (v1.0, v2.0) que añaden características, refinan funciones y adaptan la experiencia.
    
- **Utilidad y resolución de necesidades**
    Tanto un producto físico como un software se crean para resolver un problema específico o satisfacer una necesidad de un usuario (una silla sirve para sentarse; un procesador de texto, para redactar documentos).

	# Mitos
1. ¿Qué es un mito?
R.  Relato que puede o no ser verdad ejemplo: "Los gatos negros dan mala suerte.", es un mito porque la gente se lo invento y puede que si o no nadie sabe.

2. ¿Hay mitos en el desarrollo de software?
R. Si.

3. De ejemplo de 5 mitos en el desarrollo de software
Ejemplo: Qué cuando más pronto empiece a escribir código más rápido terminó.
- **"1. Agregar más programadores a un proyecto retrasado lo hará terminar más rápido"**
    _(Ley de Brooks)_ Introducir más personas a un proyecto avanzado genera mayor necesidad de comunicación, coordinación y tiempo de capacitación, lo que suele retrasar aún más las entregas.
- **"2. Una vez que entregamos el software y funciona, nuestro trabajo ha terminado"**
    El software requiere mantenimiento continuo, parches de seguridad, actualizaciones de compatibilidad y soporte para adaptarse a los cambios del entorno en el que opera.
- **"3. Si los requisitos cambian constantemente, solo hay que trabajar más horas para compensarlo"**
    Cambiar los requisitos sin un control de alcance o análisis de impacto destruye la arquitectura de la aplicación, incrementa los errores y agota al equipo sin garantizar resultados exitosos.
- **"4. La calidad del software solo depende de la habilidad de los programadores"**
    La calidad final depende de todo el proceso: desde un análisis claro de los requisitos y un buen diseño de arquitectura, hasta pruebas rigurosas y una comunicación efectiva con el cliente.
- **"5. Una base de datos de documentación exhaustiva garantiza el éxito del proyecto"**
	Llenar carpetas con manuales y especificaciones detalladas no asegura que el programa funcione ni que resuelva la necesidad real. La documentación es una herramienta de apoyo, pero la verdadera prueba del éxito es un software funcional, utilizable y bien probado.
