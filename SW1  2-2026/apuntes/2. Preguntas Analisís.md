> La etapa del `¿Qué?`
# 1. ¿Cuál es el objetivo del Analisís?
Respuesta:
- `Identificar`, `definir` y `comprender` qué es lo que el software debe hacer.
- Obtener una **especificación completa, detallada y libre de ambigüedad** acerca de lo que el software debe hacer o de lo que el cliente requiere.
- Entender el problema sin pensar todavía en la tecnología ni en la implementación.

El docente lo resume así:

> “Cuando estamos haciendo análisis, solamente nos interesa identificar, definir, comprender qué es lo que el software debe hacer.”

Y también:

> “Lo que queremos es llegar a obtener una especificación completa, detallada y libre de ambigüedad acerca de lo que el software debe hacer.”

# 2. Qué se genera como resultado o entregable del análisis?
El entregable principal es el:

> **SRS — Especificación de Requisitos de Software**  
> (_Software Requirements Specification_)

Según la clase:
- Es un **documento** que estipula la **Especificación de Requisitos de Software**.
- Es una **descripción completa, detallada y libre de ambigüedad** acerca de lo que el software debe hacer.
- Puede incluir requisitos funcionales y no funcionales, modelos, prototipos, criterios y prioridades, como mencionó un compañero, pero el nombre técnico central es **SRS**.

# 3. ¿Cuáles son las actividades que ocurren durante el análisis?
El docente pide basarse en el **Proceso Unificado**, que define dos flujos de trabajo relacionados con el análisis:
#### a) Flujo de captura de requisitos
Actividades mencionadas:
- Identificar **actores y casos de uso**.
- **Priorizar** los casos de uso.
- **Detallar** los casos de uso.
- **Estructurar** los casos de uso.
- **Elaborar** el modelo de casos de uso.
#### b) Flujo de análisis
Actividades mencionadas:
- **Análisis de paquetes**.
- **Análisis de casos de uso**.
- **Análisis de clases**.
- **Análisis de tipos** / detección y análisis de tipo.

El docente aclara que no basta con responder de forma improvisada; hay que respaldarse en métodos o estrategias aprendidas, como el Proceso Unificado.
# 4. Qué roles o trabajadores aparecen durante el análisis?
En la clase se mencionaron los siguientes roles:
- **Analista de sistemas** / analista.
- **Ingeniero de requisitos**.
- **Cliente**.
- **Usuario**.
- **Jefe de proyecto**.

El docente también comenta que en **Scrum** estos roles cambian de nombre, aunque en la transcripción no se detallan con claridad todos esos nombres.
# 5. Liste ejemplos de posible errores o defectos en un software que ya este en producción y se deba a un trabajo ineficiente durante el análisis.
Según lo conversado en clase, algunos ejemplos son:
- **El software no hace lo que el usuario realmente quiere o necesita**, debido a una **interpretación incorrecta de los requisitos**.  
    El docente señala que este es el defecto **más crítico y más caro**, porque aunque el diseño, la arquitectura y la programación estén bien hechos, se construyó algo equivocado.
- **Especificaciones incorrectas**: el equipo puede haber diseñado y programado muy bien, pero sobre requisitos mal definidos.
- **Pérdida de datos**, mencionada por un compañero como ejemplo.
- **Software ineficiente o “malogrado”**, también mencionado por un compañero.
- **Requisitos ambiguos, incompletos o mal interpretados**, que llevan a funcionalidades incorrectas o incompletas.
- **Retrabajo costoso** al descubrir tarde que el sistema no cumple con las expectativas del cliente.
> **Aclaración del docente:** un software lento puede deberse a un problema de **diseño o implementación**, no necesariamente de análisis. El error típico de análisis es que el sistema **no haga lo que el usuario quiere**, por una mala interpretación de los requisitos.
